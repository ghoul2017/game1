# 工作流程

## 任务判断

- 小任务（修 bug、调样式、加字段）：直接改，编译通过即可。
- 中等任务（新增 Handler、新面板）：改完编译并做必要验证。
- 大任务（新子系统、跨端功能）：拆解为可独立完成的步骤，逐步实现。
- 需求不清：先和用户确认范围，再动手。

## 验证要求

- 服务端改动：`dotnet build server/Server.csproj`。
- 客户端、Robot、共享代码或整体结构改动：`dotnet build game1.sln`。
- 文档-only 改动可不编译，但最终说明中要明确未运行编译。
- 验证失败就继续修；最多 3 轮后仍失败，说明原因、剩余风险和下一步。

## 需求拆解

```text
docs/1.需求.md → docs/2.PLAN/{编号}-{名称}.md → docs/3.TODO.md → 审批 → 实现
docs/4.发现需求.md → 自行发现，自行解决
```

从 `docs/1.需求.md` 新拆出的需求，计划生成后必须等待用户确认；用户在当前对话中直接下达的实现请求，按实现阶段全自动执行。

### 启动检查

1. 读 `docs/1.需求.md`，找出 `##` 描述行未标注 `[已规划]` 的需求。
2. 逐条生成计划文件到 `docs/2.PLAN/`，更新 `docs/3.TODO.md`，标注 `[已规划]`。
3. 检查 `docs/4.发现需求.md` 是否有待解决项。
4. 等待用户审批后再开始从需求文档拆出的实现。

### 文档格式

- 需求：`#` 标题 + `##` 描述；`[已审批]`/`[已完成]` 标 `#` 行，`[已规划]` 标 `##` 行。
- 计划：具体到类名、方法签名、文件路径、字段类型。
- TODO：模块/子系统级，只列做什么，不列怎么做，不写“编译验证”等执行侧事项。
- 标 `[已完成]` 前必须检查所有 `##` 描述行都有 `[已规划]`。
- 已解决遗留问题移到 `docs/7.遗留问题归档.md`，不要长期堆在当前遗留列表。

## 执行中复查

计划是指南针，不是铁律。执行前和执行中都要确认：

- 任务还有必要做吗？
- 前提假设还成立吗？
- 收益是否大于成本？
- 是否出现未重现、无法验证或用户已有改动冲突？

## Git

- 使用 `git -C <path>` 或 `git -c safe.directory=...`，不要依赖 `cd ... && git ...`。
- commit message 用中文，格式如 `feat: [F001] 功能描述` 或 `docs: 更新规则`。
- 代码实现完成后自动 commit。
- 不自动 `git push`。
- 不执行 `git reset`、`git checkout` 回退、递归删除等高风险操作，除非用户明确要求。

## 完成即停

任务目标完成、必要文档更新、验证通过并提交后停止。不要在同一轮主动延伸新需求。
