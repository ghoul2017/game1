# 架构迁移方案：IModule→Component + Handler统一 + Entity化 + MongoDB

## 背景

当前架构存在三套并行模式：
1. **IModule 模块系统 vs Component 系统** — IModule 管理生命周期，Component 管理组件挂载，两套体系并存
2. **继承式 Handler vs 扩展方法 Handler** — Bag/Mail/Chat/Map/Task/Fight 用继承式，User/Misc 用扩展方法
3. **MySQL+Redis+EntityFactory 缓存 vs MongoDB** — MySQL 存 LONGBLOB + Write-Behind 缓存，MongoDB 仅存日志

统一为：**Component 体系 + 扩展方法 Handler + MongoDB 原生 BSON 存储**。

## 决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| IModule 生命周期 | 去掉 Init/Start/Stop | 大部分是空壳，有实质逻辑的直接在 Component 或 Program 中处理 |
| EntityFactory/EntityCache/PersistTask | 全部删除 | MongoDB 原生读写替代 Write-Behind 缓存层 |
| MongoDB 存储格式 | BSON 文档 | 可直接查询，优于 Protobuf 二进制 |
| Manager 单例 | 拆解为 Component + System | Manager 数据→Component，方法→System（静态扩展方法） |
| Player 拆分 | 拆为多 Component | 符合 ECS 理念 |
| game/ 目录 | 全部迁走 | 统一到 Components/ 和 Core/ |

## Phase 4: Manager 拆解 + game/ 目录迁移 ✅

### Manager → System（拆解完成）

| 旧 Manager | 新 System | 新 Component 数据 |
|---|---|---|
| PlayerManager | PlayerSystem | PlayerComponent（_players, _playersByUserId, _playersByName） |
| BagManager | BagSystem | BagComponent（RoleBag, _nextItemUid） |
| ItemEffectManager | ItemEffectSystem | （静态方法，无状态） |
| MailManager | MailSystem | MailComponent（RoleMailList, NextMailId） |
| ChatManager | ChatSystem | ChatComponent（_lastWorldChatTime） |
| TaskManager | TaskSystem | TaskComponent（RoleTaskList） |
| FightManager | FightSystem | FightComponent（_units, _configManager） |
| MapManager | MapSystem | MapComponent（_maps, _playerMapMap, _playerMapObjMap） |
| MonsterManager | MonsterSystem | MonsterComponent（_mapMonsters, _spawnTimers, _nextMonsterId, _updateTimer） |

### System 规则
- 纯静态扩展方法类（`public static class XxxSystem`），只有方法和常量，不持有字段
- 通过 `this XxxComponent self` 访问 Component 数据
- 日志用 `LogManager.GetLogger(nameof(XxxSystem))`
