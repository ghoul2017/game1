# 工作流程

## 判断力

- 小任务（修 bug、调样式、加字段）→ 直接改，编译通过即可
- 中等任务（新增 Handler、新面板）→ 改完编译+验证
- 大任务（新子系统、跨端功能）→ 拆解为可独立完成的步骤，逐步实现
- 需求不清 → 先和用户讨论，确认范围后再动手

## 底线规则

1. **改完必须编译** — 服务端 `dotnet build server/Game`，客户端 `dotnet build client/Assembly-CSharp.csproj`。编译不过就修，修不了就回退
2. **验证不是摆设** — 代码变更后用 verify-feature + verify-quality 并行验证。验证失败就修，修不好就回退，最多 3 轮
3. **回退机制** — 修复循环耗尽后 `git checkout -- <files>` 回退，向用户说明原因
4. **知识归档** — 实现中发现有价值经验，委托 mem-writer 归档
5. **不 git push**

## 完成即停

任务完成后立刻停止。新需求的规划由用户在下次对话中触发。判断：TODO 全部勾选 + 编译通过 + 验证通过 = 停。

## 需求拆解

```
1.需求.md → 2.PLAN/{编号}-{名称}.md → 3.TODO.md → 审批 → 实现
4.发现需求.md — 自行发现，自行解决
```

**关键约束：计划生成后必须等用户确认才能开始实现。**

### 启动检查

1. 读 `docs/1.需求.md`，找出 `##` 描述行未标注 `[已规划]` 的需求
2. 逐条生成计划文件到 `docs/2.PLAN/`，更新 `docs/3.TODO.md`，标注 `[已规划]`
3. 同时检查 `docs/4.发现需求.md` 是否有待解决项
4. **等待用户审批后再开始实现**

### 需求/计划/TODO 格式要点

- 需求：`#` 标题 + `##` 描述，`[已审批]`/`[已完成]` 标 `#` 行，`[已规划]` 标 `##` 行
- 计划：必须具体到类名、方法签名、文件路径、字段类型
- TODO：粗粒度（模块/子系统级），只列做什么不列怎么做，不写"编译验证"等执行侧事项
- 标 `[已完成]` 前必须检查所有 `##` 描述行都有 `[已规划]`

## 执行前重新评估

**计划是指南针，不是铁律。** 执行前确认：任务还有必要做吗？前提假设还成立？收益大于成本？否则跳过或调整。

## Git

- `git -C <path>` 语法，不用 `cd ... && git ...`
- commit message：中文，格式 `feat: [F001] 功能描述`
- 不 push

## 子 Agent

| subagent_type | 用途 |
|--------------|------|
| dev-worker | 代码实现 |
| verify-feature | 功能需求覆盖验证 |
| verify-quality | 代码质量审查 |
| mem-writer | 知识归档 |

并行验证时同一条消息发出两个 Agent 调用，都设 `run_in_background: true`。
