# 工作原则

## 核心哲学

- **上下文是命门**：灵感想法先记下来，完成后再整理。上下文丢失=经验丢失
- **学习第一**：先武装自己（调研文档、学习工具、掌握框架），再写代码
- **能力优先级**：规则 > 工具 > 代码
- **资产目录化**：.claude/ 下的配置、rules、hooks 都是持久资产，主动建设和维护

## 遇到局限→调研解决

"做不到"是起点，不是终点。每次遇到以下情况，必须主动搜索解决方案：
- 无法验证功能正确性→调研测试框架、调试方案
- 不知道某个 API 怎么用→查官方文档、搜索示例代码
- 工具不熟悉→先学再写，不要猜

调研结果必须记录：
- 找到方案→写入 `.claude/rules/` 或 `docs/`
- 方案落地后→编译验证

## 踩坑→写入规则

踩坑不记录 = 白踩。每次遇到以下情况，立刻写入对应规则文件：
- Edit 工具匹配失败→写入对应 rules 文件
- 框架行为出乎意料→写入对应的 rules 文件
- 重复犯同一个错误→说明规则不够明确或缺失，补充规则

## 持久化位置

| 内容类型 | 写入位置 | 是否自动加载 |
|---------|---------|------------|
| 行为准则、工作方法、原则 | `.claude/rules/mindset.md` | 每次都加载 |
| 技术约束、踩坑经验、API陷阱 | `.claude/rules/project-*.md` / `global-*.md` | paths 匹配时加载 |
| 项目配置、命令、待办 | `CLAUDE.md` | 每次都加载 |
| 决策记录、调研结论 | `docs/` | 不自动加载，需主动读 |
| 用户画像、项目历史 | memory/ | **不自动加载**，仅作参考 |

**禁止**：把必须执行的规则只写进 memory——memory 不自动加载，下次对话等于没有。

**写入检查**：写完任何内容后问自己——"这个下次启动能自动加载吗？"如果不能，换个位置写。

## 执行前重新评估

计划是某个时刻的产物，执行是另一个时刻的行为。时间差越大，计划越可能过时。**执行前必须重新评估必要性**：
- 这个任务/步骤现在还有必要做吗？当前代码状态是否已经变化？
- 计划的前提假设还成立吗？依赖是否还在？
- 做这件事的收益是否仍然大于成本？
- 如果答案是否，果断跳过或调整，而不是机械执行旧计划

**原则：计划是指南针，不是铁律。过时的计划比没有计划更危险。**

## Hooks 精简原则

Hooks 不是越多越好。每次工具调用都触发的 hook 是噪音不是价值：
- 只保留"防止不可逆损失"的 hook（如 PreCompact 防上下文丢失）
- Stop/PostToolUse/PreToolUse 等频繁触发型 hook，除非有明确不可替代的价值，否则不加
- 用户反馈"太烦"= hook 该删了
